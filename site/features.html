Run agents

Start, steer, pay for and hand over the agents themselves.

Run agents

Agents you can steer mid-flight

Queue a note, steer now, pause, resume and compact a live session

The problem
A long agent run is a black box. You can wait, or you can kill it and lose the context it spent an hour building.
What changes
Every running agent stays addressable. You can queue a note for its next turn, ask it to change course now, pause it with its conversation kept, change how it behaves, and let it compact its own context, all without throwing the session away.
In practice
The Atlas conductor is mid-turn on a CSS refactor when you notice it is editing the wrong stylesheet. You send a forced message, which asks the backend to interrupt or steer the turn. Edits it already made stay on disk, so you review them. An hour later a quota window runs out, so you hold the agent and release it once the quota is back: the aborted turn is re-queued and runs again on the same conversation.

Start and talk

Claude or Codex, side by side
Spawn agents on either backend from the same cockpit; Kimi and generic OpenAI-compatible backends are also supported.
Next-turn or forced messages
A normal message waits for the next turn boundary. A forced one asks the backend to interrupt or steer the active turn; what the turn already did is not rolled back. Each send reports whether a turn started, is mid-turn, is pending or the agent is held.
Slash commands pass through
A message marked as a provider slash command, like /compact, arrives verbatim so the backend reads it as a command instead of as text.
Stall detection
If a message is delivered but no turn ever opens, the daemon raises a prompt-stalled event you can subscribe to.

Pause, resume, interrupt

Interrupt
Abort only the in-flight turn. The process stays up and addressable and can take new input.
Hold and release
Park an agent: its turn is aborted and re-queued, it does not wake on mail, and release resumes it with full context. Side effects the aborted turn already caused are not undone, and the docs say so.
Quota pauses stay put
A session-limit or crash-backoff pause is not released early by accident; you opt in when you know the quota is back.
Kill when you mean it
A real stop that ends the process, kept separate from interrupt and hold.

Change a live agent

Reconfigure in one respawn
Change model, effort, account, turn limits, budget ceiling, compaction threshold, instructions or autonomy; the conversation survives and the next turn behaves the new way.
Live changes, no respawn
Permission profile and display label apply without interrupting a running turn.
Compaction on request
Ask an agent to compact its context. Claude receives /compact, Codex gets its native compact request, and completion arrives later as an event, because acceptance is not completion.
Hand off across providers
When a quota window is spent, move an agent's context to a fresh agent on another provider or account through a portable package of brief, anchors and recent turns.
Rebind to another directory
Move an agent to a new working directory with the same provider, account and model.
Provider remote control
Turn provider-native remote control on for a live session where the CLI and account support it.

See the fleet

Fleet dashboard and lanes
Agents grouped by team or project, with live status lanes and pinned tasks or agents that keep their live fields in view.
Native sub-agent rows
A provider's own sub-agents appear as read-only shadow rows with their task, summary and metrics.
Spawn cost preview
Estimate the token cost of the Chimera tool grant a spawn would get before you spawn it. It is an estimate, never a policy.

  • Batch send and resume Message or resume several agents in one call.
  • Agents can rename themselves An agent can set its own display name.
  • Find and tail Look up agents and read their recent activity.

Providers, accounts and failover

Several accounts and providers, with failover when quota runs out

The problem
One subscription has one quota. When it runs dry mid-task, everything waiting on it stops, and juggling logins by hand does not scale past a couple of agents.
What changes
Register several accounts across providers and let Chimera route around an exhausted one, so a quota limit becomes a delay instead of a stall.
In practice
Three Atlas workers share a Claude subscription that hits its session limit. The scheduler cools that account down and moves new work to your second account. When the quota resets you clear the cooldown in one action instead of editing config.

Accounts

Several ways to log in
Subscription login, a key in the OS keychain, an environment variable, an external command that prints a key, or OAuth.
Test before you trust
Add, remove, re-key and test an account from the UI or through the account tools.
Cooldown and uncool
A spent account is cooled down; clearing it releases the agents that were paused on that account's session limit.

Failover

Across accounts
Work moves to another account of the same provider when one is exhausted.
Across providers, if you allow it
Failover can optionally cross providers; an agent can also be handed off to a fresh agent on another provider with its context.
Per-project conductor account
Pin the account, and optionally the model and permission profile, a project's conductor is born on.

Catalog

Provider and model lists
Browse the providers and the models each exposes, then pick per role, per agent or per spawn.
Your own OpenAI-compatible server
Define a custom provider with a base URL and default model, for a local Ollama, LM Studio or vLLM server. A key is only asked for if you say the server needs one.
Base URL and default model overrides
Override a built-in provider's base URL or default model, and set a per-provider context-compaction threshold. Changes apply on the next daemon start.
Early-access note
Claude and Codex are the main paths. Kimi and the generic OpenAI-compatible backend are also available.
Smaller capabilities in this area (1)
  • Clear a cooldown One action clears an account's cooldown and releases its session-limit pauses.

Permissions, approvals and budgets

Permission profiles, approvals and spend ceilings

The problem
Agents that can edit files and run commands need limits, and limits only work if they are visible, adjustable mid-run and tied to real spend.
What changes
Pick how much freedom an agent has, answer permission prompts from one place, and put a dollar ceiling on a whole tree of agents instead of watching a meter.
In practice
A research sub-agent on Atlas starts under the read-only profile. When it asks to run a command, the request lands in your inbox; you allow it once. Later the whole spawn tree crosses its budget ceiling, so the tree pauses and tells you instead of quietly continuing.

Permission profiles

Read-only, accept edits, full
Three profiles per backend, overridable per project or per spawn, and changeable on a live agent without a respawn.
Approvals in one feed
Pending permission requests show up in the attention inbox and can be answered allow or deny from there.
Single-writer write gate
A worktree has one writer at a time. A dry run tells you whether writing certain paths would be refused and why; the mode is enforce, warn or off.

Budgets and usage

Ceilings on a spawn tree
A budget covers a whole tree of agents. A breach pauses the tree. Budget warnings are an event you can subscribe to.
Per-agent ceilings
Set a maximum spend on one agent through reconfigure.
Usage and performance
Query usage, and read latency, tokens, cost, gate failures and error rates by team, provider or workflow.
Honest about estimates
Some budgets are estimated from token counts, not from a provider invoice.

Host tools

Allow, ask or deny per CLI tool
Chimera scans the command-line tools on the host and keeps an allow, ask or deny policy per tool and profile, with a wildcard row.
Smaller capabilities in this area (2)
  • Write-gate dry run Ask whether writing given paths would be refused, and which check refused it.
  • Host tool scan cache The host CLI tool scan is cached for about fifteen minutes.

Voice and meetings

Talk to agents and run meeting rooms

The problem
Some conversations with an agent are faster spoken than typed, and some decisions need several agents and you in the same room.
What changes
Talk to an agent on its existing authenticated session, or open a bounded meeting room with an approved roster. Consent is explicit and the coding work keeps running when audio ends.
In practice
Before a refactor, you open a meeting room for the Atlas conductor and two workers. You approve the roster, set a duration and utterance budget, and give desktop consent. When the call ends, the coding work carries on.

Limits. Voice is a preview. It needs the desktop app for microphone consent and is not part of the baseline workflow.

Native voice

Per-agent opt-in
Native Codex voice runs on an agent's existing authenticated thread, only for agents you opt in, with microphone consent in the desktop UI.
Push to talk
A separate path transcribes your speech to text for agents that have no native voice.

Meeting rooms

Approved roster
A room has a named roster; editing the roster renews consent.
Budgets
A duration and utterance budget bound each room.
Audio is separate from work
Ending audio does not stop agents' coding work. Create, list, update, end and delete rooms through the voice-room tools.

Organize the work

Projects and conductors

Bind a repo to teams, a queue and an always-on conductor

The problem
Real work lives in repositories. Without a project boundary, agents, queues and memory blur together and every new session starts cold.
What changes
A project binds a repository to its teams, queue and conductor. Work routed to the project lands on the right team, with the right permissions and account.
In practice
You import the Atlas website repository from a git URL, assign the web team, and start its conductor. A new task is dispatched to the project and lands on the bound queue instead of a random worker.

Create and organize

Create or import
Register an existing directory, or clone a git URL (file URLs included).
Assign teams
Attach one or more teams to a project, and archive, restore or delete it later.
Per-project permissions
Override the default permission profile for one project's conductor.

Conductors

Start and stop a conductor
Each project can run a conductor that coordinates its teams. It always starts with full autonomy and orchestration enabled.
Pin the conductor's account
Choose the account, model and profile the conductor is born on. Restart the conductor for a change to take effect.

Routing

Dispatch by preference
A bound queue first, then a fitting role on the project's team, then the global pool, and a direct spawn only as a last resort. The reply says what actually happened.
Live sessions and checkpoints
The project screen shows live sessions, checkpoints and its setup settings in one place.

Roles with per-team overrides

Reusable settings, with per-team overrides you can see

The problem
Copying the same instructions, model and tool limits into every spawn drifts quickly, and one tweak for one team should not change every other team.
What changes
Define a role once in a library. Teams bind it, inherit its fields and pin only what differs. The editor shows which values are inherited and which are overridden.
In practice
A reviewer role in the library uses a careful model and read-only tools. The Atlas team binds it and pins a different working directory. Other teams keep inheriting the library value.

The role library

What a role holds
Model, effort, permission profile, instructions, plugins, skills, an MCP tool allowlist, account, turn limits, isolation and worker pool size.
Templates, not live agents
Editing a role changes future spawns, not agents already running from it. The form says how many are live.

Binding overrides

Inherited versus pinned
For each field the editor shows the library value in grey as inherited, or the pinned override highlighted, with a toggle between them.
Editable any time
Overrides can be edited after a role is already bound, without a separate edit mode.
Provenance badges
Team members show where each role setting comes from.

Teams that share a queue

Named groups of agents with a shared queue and concurrency

The problem
A handful of agents with no structure step on each other and nobody knows who is free.
What changes
A team is a named group of role-bound workers tied to a queue with a concurrency cap. Work is routed to a free worker of the right role.
In practice
The Atlas team has a developer and a reviewer role and a cap of two concurrent workers. Push five tasks and two start; the rest wait their turn, and the team view shows who is working on what.

Members and roles

Live workers

Edit in place

Work with a team

Assign by team and role
Route a task to a free or idle worker of a role through the team's queue, or to one agent directly.
Team-aware messaging
An agent can see its own team and message the whole team.

Organize the work

Queues with priorities and dependencies

Prioritized tasks with dependencies and retries

The problem
A pile of tasks in a chat window has no order, no memory of what depends on what, and no answer to why something is not running.
What changes
Queues order work by priority and arrival, hold tasks until their dependencies finish, retry failures, and tell you exactly why a task has not started.
In practice
On Atlas, a tests task depends on a refactor task. You add a late dependency instead of writing run this last in a prompt. The tests task stays blocked, and an explain call names the unmet dependency.

Ordering

Priority then first-in
Priority breaks ties among ready tasks; arrival order does the rest.
Dependencies are constraints
A task will not run until what it depends on is done, and cascades to failed if a dependency fails. Self-dependencies and cycles are rejected.

Control

Pause and resume
Stop dispatch from a queue without losing its tasks.
Edit, move, cancel, retry, requeue
Fix a pending task, move it between queues, cancel it, or retry a failed one.
Retries
Failed tasks retry under a bounded policy.

Explain and recover

Why is this not running?
One call evaluates the scheduler's own ordered checks: team binding, queue paused, task state, dependencies, drain order, role, concurrency, workflow binding and spawn limits. It names the first one that blocked.
Remediation jumps backward
A step configured for remediation can request a bounded jump to an earlier step with a correction brief when the real root cause is upstream.
A default gate workflow
Queued tasks run through a gated workflow by default.
Smaller capabilities in this area (2)
  • Assign versus dispatch Assign targets an agent or a team and role. Dispatch follows the project's routing preference.
  • Cycle-safe dependencies Adding a dependency to a pending task rejects self-dependency and cycles.

Organize the work

Workflows with real gates

Multi-step plans with gates, fan-out and loops

The problem
Agents say they are done. Without an independent check, done only means stopped talking.
What changes
Describe the steps as a graph and gate each one on something that can fail: a command, an artifact, a human approval or a critic loop.
In practice
The Atlas release workflow builds, fans out three reviewers, joins their findings and waits at a human approval gate. If the test command fails, the task loops back to the fix step a bounded number of times and then stops for you.

Shape

A graph of steps
Steps form a DAG with routing conditions, bounded loop-back, fan-out and join, and sub-workflows.
Plan a workflow from a goal
A planning step can design the workflow at runtime and compile it as a sub-workflow, under the same gate, checkpoint and budget rules.

Gates

Four kinds
A shell command, an artifact check, a human approval, or an evaluator-optimizer critic loop.
On failure
Retry, loop back, or request remediation from an earlier step.

Author and inspect

Workflow studio
Create, edit, run and inspect workflows in the app.
A durable step journal
One entry per step attempt with model, account, tokens, cost, gate outcome and timings. It survives daemon restarts and the queue's terminal-task eviction.

  • Step journal filters Filter the journal by task, agent, step, queue, team or outcome.

Organize the work

Scheduled jobs that survive sleep

Cron, interval and one-shot jobs that run unattended

The problem
Recurring work, like a nightly dependency check, normally means a cron entry on one machine that nobody remembers and nothing records.
What changes
Schedule agent work by cron, interval or once. Each run is recorded with how it was triggered and how it ended, and a laptop that was asleep does not silently lose a run.
In practice
A nightly job on the Atlas team checks for outdated packages at 02:00 in your timezone. The laptop was asleep, so the run is marked late and coalesced. A failed run retries, and after repeated failure lands in the dead letter list until you requeue it.

Cadence and target

Cron, interval, one-shot
With an explicit timezone, and next-run time shown for each job.
Three kinds of target
A team and role, an inline agent definition, or an existing agent that is resumed if paused. A killed or missing target disables the job.
Prompt templates
Use the job name, timestamp, ISO time or agent id in the prompt.

Reliability

Overlap policy
Decide what happens when a run is still going at the next tick.
Catch-up
Optionally run a missed occurrence if it is not staler than a limit you set.
Sleep and wake
Runs that come due while the machine slept coalesce unless wake is enabled on macOS. Sleep-wake runs record how late they were.
Budget ceiling per job
Cap what one run may spend.
Retries and dead letter
A bounded retry budget, then a dead-letter state. Requeue revives a dead-lettered job, resets its retries and re-arms the next occurrence.

Operate

Run now and snooze
Fire a job on demand, or snooze it until later.
Run history
Each run records whether it was scheduled, manual or catch-up, and whether it was ok, failed or skipped.
Import and export
Move a schedule definition between installs.
Smaller capabilities in this area (2)
  • Sleep-wake records A run that fired late after sleep records its trigger and how late it was.
  • Dead-letter event A dead-lettered job raises an event you can subscribe to.

Connect and extend

Tools, secrets, desktop control, skills, hooks and other machines, with controls over what each can reach.

Connect and extend

MCP store with trust and OAuth

MCP servers with trust levels, OAuth and discovery

The problem
Every MCP server you add is code with access to your agent. Wiring them into each client by hand leaves nothing you can review.
What changes
One store holds every MCP server. An agent's proposal arrives disabled and untrusted, and agents can propose servers but cannot enable, trust, add credentials to or sign in to them. Calls to an untrusted server that can write ask first.
In practice
An Atlas agent proposes an HTTP MCP server it found. It appears in Settings as a disabled, untrusted proposal. You review it, sign in with OAuth yourself and mark it trusted. Until you enable it, agents cannot call its tools. The daemon may still run its guarded, unauthenticated OAuth metadata check to see how the server signs in, and the sign-in itself stays a human step.

Install and trust

Disabled and untrusted proposals
An agent's proposal and a package installed from the store are saved disabled and untrusted. Servers imported from Claude or Codex config come in enabled and fully trusted. Either can be changed afterwards. Trust is full or untrusted, and unknown means untrusted.
Approval on risky calls
A call to an untrusted server that may write asks for approval. Calls the server hints are read-only are allowed.
Reviewed packages
Package-based servers are reviewed before install, with lifecycle scripts off.
Built-in servers
Chimera's own browser and desktop servers and the Laya server are built in and cannot be uninstalled.

Discover and import

Import from Claude and Codex
Find the servers already configured in those clients and import them. Imports arrive enabled and fully trusted, so look them over, and switch trust down for any you want approvals on.
OAuth discovery
For a remote URL you add or import, the daemon makes an unauthenticated request for public OAuth metadata through an SSRF guard: public addresses only, redirects re-checked, time and size bounded. If it finds an authorization server the entry defaults to OAuth. This can happen while the server is disabled, and an inconclusive result never blocks the add. A localhost or LAN server is stored but not auto-detected, so choose its auth type yourself. The same public-only rule holds when an untrusted entry, such as an agent's proposal, signs in. A fully trusted entry may use private addresses, and so may the live connection of any server you enable, so a local MCP server keeps working.
Agents can propose
An agent's proposal is a disabled, untrusted entry for you to review. It cannot enable or trust it, add headers or credentials, or complete OAuth, and it does not install a package.

Operate

OAuth and bearer
HTTP servers use bearer tokens or OAuth, with a status chip and a re-authorize action.
Session modes
Share one session, give each agent its own, or take it exclusively.
Direct or proxy-only
Choose whether agents see a server's native tools or reach them only through the proxy.

Both directions

Chimera as an MCP server
Claude Code, Codex or any stdio MCP client can drive Chimera through its MCP server. A small core of tools (spawn, wait, send, ask, memory, team basics) is always visible; the rest are found and called on demand, so their schemas are not sent on every turn.
One tool surface out
The same store connects Chimera out to other MCP servers, so agents reach one set of tools instead of every client configuring the same servers.

A secrets manager with grants and an audit trail

Named secrets with per-agent grants and an audit trail

The problem
Agents need tokens, and pasting them into prompts or committing them next to the code puts them in logs and transcripts.
What changes
Store a secret once, grant it to specific agents in a mode you choose, and have every read audited. Values are stored in the system keychain.
In practice
The Atlas deploy agent gets a deploy token in inject mode: it appears as an environment variable the next time the agent starts. A review agent gets reveal mode and has to read it through the secret tool, which writes an audit entry each time.

Limits. On macOS the value is passed to the keychain command as an argument, so it is briefly visible to other local processes. A corrupt secrets file makes the daemon refuse to start rather than guess.

Store

System keychain
Values go to the system keychain. The secrets file holds only names, descriptions and grants, never values, and is private to your user.
Names, not values, in the UI
The settings screen shows names, descriptions and masked state.

Grant

Inject or reveal
Inject sets an environment variable at the agent's next start. Reveal lets the agent read the value through a tool.
Uniform denial
An agent that is not granted a secret, one that is granted inject only, and a secret that does not exist all look the same.
Agents list only their own grants
An agent cannot enumerate secrets it was not given.

Audit and operate

Audit
Writes, grants and reads are recorded, with allow or deny for grants and reads.
Redaction
A value an agent revealed is registered for redaction in logs.
Operator-only management
Setting, deleting, granting and revoking are not exposed to agents through MCP.
Smaller capabilities in this area (1)
  • Corrupt file fails closed A corrupt secrets file stops the daemon instead of silently losing grants.

Browser and desktop control, with a monitor

Browser, desktop control and optional Laya assistance

The problem
An agent that can click and type on your machine is powerful and risky, and you need to see what it is doing and stop it.
What changes
Give agents a headless browser or, on macOS, control of the real desktop, optionally with Laya, a local assistant that ranks candidate actions. While an agent holds the desktop, a live preview appears in that agent's own transcript with a Stop button. Desktop control is exclusive, so two agents never fight over the mouse.
In practice
An Atlas agent drives the macOS desktop to check how the staging page renders in your real browser window. A small preview sits at the upper right of that agent's transcript with the target window and the latest actions. When one looks wrong, you press Stop desktop control.

Limits. Desktop control and Laya are macOS only. Laya only helps rank actions: the exclusive lease and the Stop button apply the same way with or without it.

Three ways in

Laya (optional)
Optional local action-ranking assistance for computer use. It needs macOS 14 or later. You install it from the Computer use card, which downloads one English model pinned to a full revision and checked against a digest; after that it runs offline. It is English-only: a multilingual or typed-decision request fails rather than fetching a model Chimera has not reviewed.
Headless browser
Browser automation without a window, with its own session for each agent; not supported on Linux arm64 or Windows arm64. The lease and the live preview below belong to desktop control, not to this.
Desktop control
Control the real desktop, which an agent has to acquire first. macOS only.

Stay in control

Exclusive desktop lease
An agent acquires and releases desktop control, so only one controls it at a time. A call in progress cannot be taken over, and an idle lease expires after five minutes.
Preview in the owner's transcript
The monitor sits at the upper right of the transcript of the agent that holds the lease, and only there. It shows the lease owner, whether it is busy, the target window and recent tool outcomes.
Hide is not Stop
Hiding or collapsing the preview only pauses the preview; the agent keeps control. Stop desktop control ends it and also turns off automatic startup.
Not a recorder
The monitor does not keep screenshots, typed text or call arguments.

Event subscriptions and hooks

Rules on daemon events that notify, queue work or run a command

The problem
Polling for an event wastes tokens, and reacting to one automatically usually means a custom script.
What changes
An agent can sleep until an event arrives. A hook reacts to an event with no agent in the loop: notify, queue a task, spawn, run a sandboxed command, or send a notification.
In practice
A hook on Atlas pushes a regression-check task whenever code lands on main. A notify rule sends an OS notification when a queue drains, throttled so it does not repeat.

Subscriptions

Wake on an event
Subscribe, then end your turn. Topics include agent settled or spawned, task state, gate verdict, queue drained, repo landed, memory added, permission or question pending, budget warning, system woke, prompt stalled and job dead-lettered.
Filters
Narrow by agent, tree, task, queue, team, state or tags.

Hooks and notifications

Durable hooks
Run actions when a matching event fires: notify an agent, push a task, spawn an agent, run a local command or send a notification.
Channels
Toast, OS notification or webhook.
Notify rules
Event, filter, channel and throttle per rule, with a test button that bypasses the throttle.
Last fired
The hooks card shows when a rule last fired or was suppressed.

Federation across machines

Connect Chimera instances across machines

The problem
Sometimes the machine with the repository or the GPU is not the one you are sitting at.
What changes
Pair Chimera installs so one can see another's agents and, only if you allow it, start work there. Peers are read-only by default.
In practice
You pair your laptop with a desktop that holds the Atlas build cache. The peer is read-only until you explicitly allow it to spawn, and then only with the accounts you listed.

Limits. Federation is the most experimental surface, with little everyday use. It is configured as peers in config, not a single switch.

Safe by default

Read-only peers
Per-peer spawn permission defaults to off. The account allowlist defaults to none, and concurrency is capped.
Provider keys stay local
Peers exchange account names, never keys or tokens. Configuration and the account set stay on each machine. The one secret that travels is the single-use pairing token inside the invite.

Connect

SSH-tunneled socket
Pinned host keys and a dedicated restricted key; optional Cloudflare Access in front.
Pairing by invite
The raw token appears only in the invite blob. Lists show hashes, and the host key is pinned on first use.
Peer status
A local snapshot of peers' last-known status and cached host-tool summaries.

Where this stands today

Chimera is early access software. The guide describes what the code does; it does not promise polish everywhere.

  • macOS on Apple Silicon is the most tested platform. The Intel Mac build and the Linux AppImage have not yet been verified end to end on a clean machine, and on Windows only the CLI and MCP server install.
  • One command installs the signed desktop app and the CLI on macOS and Linux; the install steps are on the home page.
  • Voice and meetings is preview. Voice is a preview. It needs the desktop app for microphone consent and is not part of the baseline workflow.
  • Federation is experimental. Federation is the most experimental surface, with little everyday use. It is configured as peers in config, not a single switch.
